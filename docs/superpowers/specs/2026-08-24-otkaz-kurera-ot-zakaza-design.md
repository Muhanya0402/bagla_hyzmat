# Отказ курьера от взятого заказа

Дата: 2026-08-24

## Задача

Курьер взял заказ, но выполнить его не может — сломался транспорт, заболел, не успевает.
Сейчас выхода нет: отменить заказ может только магазин (кнопка стоит под условием `isShop`),
и курьеру остаётся звонить и просить. Заказ должен возвращаться в свободные, но эта ситуация
обязана отличаться от отказа клиента на месте и от отмены магазином — у них разные виновные и
разные последствия для жетонов.

## Что есть сейчас

- Статусы заказа: `published`, `active`, `completed`, `canceled`. Промежуточных нет.
- Отменяет только магазин, через `OrderService.cancelOrderIfOpen` (условный bulk-PATCH).
- Причины отмены — плоский список для магазина: клиент отказался / курьер опаздывает /
  неверный адрес / другое. Пишутся строкой в `cancel_reason`, `cancelled_by` всегда `shop`.
- Жетон списывает флоу «Списание баллов» при переходе заказа в `active`.
- Возврата жетонов нет нигде.
- `app_settings.top_up_enabled` сейчас `false`, у всех заказов `points_amount = 0` —
  экономика жетонов фактически стоит.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Объём | Все ситуации, кроме автовозврата по истёкшему дедлайну |
| Жетон | По инициатору: курьер вернул сам — сгорает; отменил магазин или отказался клиент — возвращается |
| Кто отмечает отказ клиента | Только магазин, как сейчас. Новый статус и экран разбора не нужны |
| Защита от злоупотребления | Лимит возвратов за скользящие сутки |
| Где живёт логика | Webhook-флоу в Directus, не в приложении |

Логика вынесена на сервер по той же причине, по которой туда переехало взятие заказа: пока
проверку делал клиент, один заказ уходил двум курьерам. Лимит, проверяемый приложением,
обходится подменённым клиентом.

## Данные

**Новая коллекция `order_returns`** — журнал возвратов. Нужна не ради истории, а как механизм:
по ней считается лимит.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | integer, auto | |
| `date_created` | timestamp | системное, по нему считается лимит |
| `order_id` | integer | обычное число, не связь — запись переживает удаление заказа |
| `courier_id` | m2o → `customers` | кто вернул |
| `reason` | string | код: `breakdown` / `illness` / `no_time` / `other` |
| `comment` | text, nullable | свободный текст курьера |

Лимит считается запросом «сколько записей у курьера за последние 24 часа». Счётчик в профиле
(как `monthly_free_used` / `monthly_free_reset`) отвергнут: он требует задания на сброс, а это
отдельная точка отказа — не отработало, и курьер либо заблокирован навсегда, либо получает
бесконечный лимит. Подсчёт по датам не имеет состояния.

Сутки скользящие, не календарные: иначе лимит обнуляется в полночь и это легко обыграть.

**Новое поле `app_settings.courier_returns_per_day`** — integer, значение по умолчанию 2.
Рядом с `top_up_enabled`, управляется без пересборки приложения.

## Возврат заказа

**Webhook-флоу «Возврат заказа курьером».** Приложение шлёт `order_id`, `reason`, `comment`.

Курьер берётся из `$accountability.user`, а **не из тела запроса** — иначе подменённый клиент
вернёт чужой заказ.

Шаги:

1. `read_courier` — `customers` где `directus_user = {{$accountability.user}}`; поля `id`, `role`.
2. `read_order` — заказ по `order_id`; поля `id`, `order_status`, `courierId.item:customers.id`,
   `points_amount`, `shopId.item:customers.id`.
3. `read_returns` — `order_returns` где `courier_id = <курьер>` и
   `date_created >= $NOW(-1 day)`; поля `id`.
4. `read_settings` — `app_settings`; поле `courier_returns_per_day`. `top_up_enabled` здесь
   не нужен: сам возврат жетоны не двигает.
5. `validate` (exec) — проверяет по порядку и бросает понятную ошибку на каждом провале:
   - заказ найден и `order_status = active` → иначе `ORDER_NOT_ACTIVE`;
   - `courierId` совпадает с курьером из авторизации → иначе `NOT_YOUR_ORDER`;
   - число возвратов за сутки меньше лимита → иначе `LIMIT_REACHED` (в ответ кладётся лимит
     и текущее число, чтобы приложение показало «осталось N»).
6. `do_return` (item-update, `$full`) — `order_status = published`, `courierId = []`,
   `courier_phone = null`, `points_charged = false`.
7. `log_return` (item-create) — запись в `order_returns`.
8. Ответ приложению: `{ ok: true, returns_left: N }` либо код ошибки.

Новый статус не заводится намеренно: `published` уже понимают все фильтры, значки, ленты и
флоу. Новый статус пришлось бы учить каждому из этих мест без выигрыша.

## Жетоны

### Сгорание при возврате курьером

Действий не требуется: списание уже произошло, возврат просто не делается.

### Починка повторного списания

Флоу «Списание баллов» останавливается, если у заказа `points_charged = true` **или** если по
заказу уже есть debit-транзакция. Обе проверки привязаны к заказу, а не к паре «заказ + курьер».
Без правки следующий курьер повезёт бесплатно.

- при возврате сбрасывается `points_charged = false` (шаг `do_return`);
- шаг `item_read_ldzoa` меняет фильтр с «есть debit по заказу» на «есть debit по заказу
  **у этого курьера**»: добавляется условие `customer_id._some.item = {{item_read_b60iz[0].courierId[0].item}}`.

Тогда второй курьер платит, а повторное срабатывание для того же курьера по-прежнему блокируется.

### Возврат жетона при отмене магазином

**Новый event-флоу «Возврат жетона при отмене».** Триггер: `items.update` на `orders`.

Условия: `order_status` стал `canceled`/`cancelled`; у заказа был назначен курьер; по паре
«заказ + курьер» есть debit; credit по этой паре ещё нет. Тогда создаётся credit-транзакция и
увеличивается `balance_points` курьера.

Проверка на существующий credit обязательна: без неё повторное срабатывание удвоит баланс.

### Связь с галочкой «Пополнение жетонов доступно»

При `app_settings.top_up_enabled = false` жетоны не двигаются вообще: списание при взятии
пропускается, сгорать при возврате нечему, возвращать при отмене нечего. Отбирать жетон у
курьера, который не может пополнить баланс, — тупик, из которого он не выберется.

Исключение: если debit произошёл **до** выключения галочки, а отмена случилась после — жетон
всё равно возвращается, иначе он зависает из-за случайного момента переключения.

Проверка добавляется в трёх местах:

- «Списание баллов» — при выключенной галочке списание пропускается;
- «Возврат жетона при отмене» — при выключенной возвращать нечего, кроме описанного исключения;
- **модалка отказа в приложении** — предупреждение «жетон сгорит» показывается только когда
  галочка включена И у заказа `points_amount > 0`. Иначе курьер видел бы угрозу, которая ни к
  чему не приведёт.

## Приложение

**Кнопка «Отказаться от заказа»** у курьера на заказе в статусе `active` — в карточке
(`order_card.dart`) и в деталях (`order_detail_screen.dart`), рядом с «Завершить». Оформление
как у отмены у магазина, но с другим текстом, чтобы два разных действия не выглядели одинаково.

**Модалка причины.** `CancelReasonModal` уже умеет нужное — список причин, комментарий,
отправка, — но жёстко зашита на отмену магазином: сама формирует список причин и сама вызывает
`cancelOrderIfOpen`. Эти две вещи выносятся в параметры, и модалка переиспользуется. Копировать
триста строк вёрстки ради другого списка причин не нужно.

Причины для курьера: сломался транспорт / заболел / не успеваю по времени / другое.

**Разбор ответа** — три исхода: получилось; `NOT_YOUR_ORDER` → «заказ уже не ваш»;
`LIMIT_REACHED` → «лимит на сегодня исчерпан» с числом оставшихся возвратов.

После успеха заказ уходит из «Моих заказов», шторка активных заказов пересобирается.

## Уведомления

**Магазину** — «Курьер отказался, заказ снова свободен».

Отдельный механизм не нужен. Во флоу «Уведомление - Изменение статуса заказа» уже есть ветка
`published` с текстом «Заказ создан». Она не срабатывает никогда: флоу висит на обновлении, а
при создании заказа обновления нет. Возврат — первый случай, когда заказ переходит в `published`
именно обновлением. Достаточно поменять текст в этой ветке.

**Другим курьерам** пуш не отправляется. Заказ снова появляется в ленте, открытые приложения
увидят его через WebSocket. Рассылать всем пуш о заказе, который уже висел, — лишний шум.

## Краевые случаи

| Случай | Поведение |
|---|---|
| Курьер жмёт «отказаться», пока магазин отменяет заказ | Условие «статус `active` и курьер тот самый» не совпадёт → `NOT_YOUR_ORDER` |
| Уникальный индекс на `orders_courierId` | Очистка `courierId` — удаление строки; индекс срабатывает только на вставку, конфликта нет |
| Фильтр прав `orders.update` | Флоу обновляет заказ с `$full`, фильтр ему не помеха |
| Дедлайн заказа истёк | Возврат разрешён; автовозврат по дедлайну вне объёма |
| Заказ уже завершён или отменён | `ORDER_NOT_ACTIVE` |

## Проверка

**Юнит-тесты** — разбор ответа флоу (успех / лимит / чужой заказ) и подсчёт оставшихся
возвратов. Это то же место, где уже была ошибка при взятии заказа: пустой ответ сервера нельзя
трактовать как успех.

**На живом сервере** — возврат заказа; повторное взятие другим курьером с корректным списанием;
срабатывание лимита на третьем возврате подряд; возврат жетона при отмене магазином.

## Вне объёма

- Автоматический возврат заказа по истёкшему дедлайну.
- Отметка «клиент отказался» самим курьером — остаётся за магазином.
- Рейтинг курьера и влияние возвратов на него.
