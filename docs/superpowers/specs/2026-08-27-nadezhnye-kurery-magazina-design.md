# Надёжные курьеры магазина

Дата: 2026-08-27
Версия приложения: 1.0.0 (3)

## Задача

Заведения с дорогим товаром отдают его тому, кто первым нажал «Взять». Магазин не выбирает,
кому вручает золото или технику, и не может ограничить круг. Нужна возможность закрепить за
магазином круг курьеров, которым он доверяет, и отдавать дорогие заказы только им.

## Что есть сейчас

- Лента курьера — все заказы, где `courierId` пуст и статус не `completed`/`canceled`.
  Ограничений по магазину нет никаких.
- Видимость задана **в пяти независимых местах**. Резать решено в четырёх — чтение остаётся
  открытым осознанно (см. ниже):

  | Место | Что решает | Состояние |
  |---|---|---|
  | `OrderService.getOrders` | список при открытии экрана | фильтр по роли |
  | `OrderRealtimeService._buildFilter` | живая лента WS | в коде помечен «дублирует логику» |
  | Право `orders.read` №163 | что вообще можно прочитать | **фильтра нет — открыто всё** |
  | Право `orders.update` №164 | кто физически может взять | ветка `courierId._null` пускает любого |
  | Флоу «Уведомление - Новый заказ», шаг `item_read_e9p2k` | кому уходит пуш | все активные курьеры |

- Постоянные пары уже сложились сами: 27 пар «магазин-курьер» с историей. У магазина 278
  курьер 280 возил 23 раза, курьер 263 — 22 раза. Списки не надо набивать с нуля.
- Масштаб: 30 курьеров, 7 магазинов, 141 заказ. Суммы 21–600 манат, медиана 180.
- У курьеров лежат `passport_scan` и `selfie_scan`. Магазину сейчас показывается только телефон.

## Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Никто из надёжных не взял | Заказ **не открывается никому**. Магазин отменяет и создаёт заново | Решение пользователя. Контроль важнее скорости |
| Кто наполняет список | Магазин из истории своих заказов **и** админ в Directus | Обе стороны, списки растут сами |
| Кому доступен режим | Включается **автоматически по сумме** заказа | Магазин не должен помнить про галочку |
| Новый статус заказа | НЕ вводится | Как и в спеке возврата: новый статус пришлось бы учить каждому фильтру, значку и флоу |
| Эскалация по времени | НЕ делается | Следствие «не открывать никогда» — конструкция упрощается до одной галочки |

### Защита от мёртвого заказа

Автоматическое включение и «никогда не открывать» вместе дают ловушку: магазин с пустым
списком создаёт дорогой заказ, тот молча помечается «для своих» и становится невидим для
всех навсегда. Магазин при этом ничего не нажимал и не поймёт, почему тишина.

**Автоматический режим срабатывает только при непустом списке надёжных.** Список пуст — заказ
уходит всем, а магазину показывается подсказка. Это единственное место, где система отступает
от буквального «дорогой значит для своих», и отступает намеренно.

## Данные

**Новая коллекция `shop_trusted_couriers`** — кто кому доверяет.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | integer, auto | |
| `shop_id` | m2o → `customers` | магазин |
| `courier_id` | m2o → `customers` | курьер |
| `date_created` | timestamp | |
| `added_by` | string | `shop` или `admin` — видно, кто добавил |

UNIQUE-индекс на паре `(shop_id, courier_id)`: без него магазин добавит одного курьера дважды
и в списке появятся дубли. Тот же приём уже стоит на `orders_courierId`.

**Поле-алиас `customers.trusted_couriers`** — o2m на `shop_trusted_couriers.shop_id`. Нужно не
для админки, а чтобы фильтр видимости мог пройти путь `заказ → магазин → его список`.

**Поле `orders.trusted_only`** — boolean, по умолчанию `false`.

**Поле `app_settings.trusted_amount_threshold`** — integer, сумма в манатах. `0` = режим выключен
целиком. Управляется без пересборки приложения.

### Обратная совместимость — обязательный шаг

У 141 существующего заказа `trusted_only` будет `NULL`. В SQL `NULL <> true` даёт не «истину», а
`NULL`, поэтому фильтр вида `trusted_only != true` **исключит все старые заказы** — курьеры разом
потеряют ленту. Два действия, оба обязательны:

1. Проставить `trusted_only = false` всем существующим заказам.
2. В самом фильтре всё равно писать `_or: [ trusted_only null, trusted_only = false ]`, а не
   `_neq: true` — на случай записей, созданных в обход приложения.

## Видимость

Фильтр свободных заказов для курьера:

```
courierId пуст
И статус не completed/canceled
И (
     trusted_only пусто ИЛИ false          -- обычный заказ, виден всем
   ИЛИ
     я есть в списке надёжных этого магазина
)
```

Путь до списка: `shopId.item:customers.trusted_couriers.courier_id`. В приложении сравниваем с
`id` курьера, в правах Directus — с `directus_user._eq $CURRENT_USER` (синтаксис `item:customers`
в правах уже проверен и работает — право №164).

⚠️ **Непроверенное допущение.** Путь получается на пять уровней вглубь, через M2A и o2m.
Проверены три уровня. Первым шагом реализации — создать коллекцию и прогнать этот фильтр
живым запросом. Если Directus его не потянет, запасной вариант: денормализовать список
курьеров в поле самого заказа при создании (`trusted_courier_ids`, csv) — фильтр становится
плоским `_in`, ценой того, что изменение списка не влияет на уже созданные заказы.

### Право `orders.read` — решено оставить открытым

Чтение остаётся без фильтра (решение пользователя от 27.08). Что это значит по-честному:

- заказ «для своих» скрыт в приложении, но **читается прямым запросом к API** мимо него;
- **взять его всё равно нельзя** — замок это право `orders.update` №164, а не чтение;
- то есть наружу утекают сведения о заказе, а не контроль над ним.

Цена решения — информационная, и она заметно меньше, чем казалось при первом разборе:
функция работает, а не изображает работу.

Одно следствие обязательно к исполнению: **фильтр пушей перестаёт быть необязательным**.
Курьер вне списка, получив пуш, откроет по нему экран заказа (чтение-то открыто) и упрётся
в отказ при нажатии «Взять». Значит, рассылку надо резать вместе с лентой.

Фильтр на чтение можно поставить позже отдельной задачей — конструкция этого не запрещает,
выражение для него уже выписано выше.

### Право `orders.update`

В ветке `courierId._null` права №164 добавляется то же условие. Это настоящий замок: без него
курьер, узнавший id заказа, возьмёт его мимо ленты.

### Пуши

Шаг `item_read_e9p2k` читает всех активных курьеров. Для заказа с `trusted_only` он должен читать
только надёжных этого магазина, иначе тридцать человек получат пуш о заказе, который видят трое.
Порядок шагов: прочитать заказ вместе со списком магазина → exec собирает id получателей →
чтение `customers` по `id._in`.

## Включение режима

Галочку ставит **приложение при создании заказа**, а не отдельный флоу. Причина в гонке: флоу
«Уведомление - Новый заказ» срабатывает на создание немедленно, и если помечать заказ вторым
флоу, пуши всем тридцати уже уйдут.

Подмены здесь можно не бояться: единственный, кто мог бы соврать про `trusted_only`, — сам
магазин, и соврал бы он в ущерб своему же товару. А вот **видимость** проверяется только на
сервере, потому что там заинтересованная сторона — чужой курьер.

Условие: `total_amount >= trusted_amount_threshold` И список магазина не пуст. Магазин видит
пометку и может снять её вручную на конкретном заказе.

## Приложение

**Магазин.**
- Экран «Надёжные курьеры» в профиле: список, удаление, добавление.
- Добавление из истории: курьеры, которые возили у этого магазина, с подсказкой «возил у вас
  23 раза» — самый естественный способ, учитывая что пары уже сложились.
- При создании дорогого заказа — заметка «этот заказ увидят только ваши надёжные курьеры»
  и возможность снять.
- Если сумма выше порога, а список пуст — подсказка добавить курьеров.
- На карточке заказа значок «Только надёжные».

**Курьер.**
- Заказ помечен «Надёжный заказ» — чтобы курьер понимал, почему заказ у него есть, а у других
  разговоров о нём нет.
- Уведомление при добавлении в список: «Магазин X добавил вас в надёжные курьеры». Необязательно,
  но это ровно тот сигнал, ради которого курьер держится за магазин.

## Второй слой: кого магазин видит у прилавка

Список даёт магазину уверенность, но кражу он не предотвращает — курьер из списка может украсть
ровно так же. Единственное место в цепочке, где подмену реально поймать, — момент выдачи товара.

У каждого курьера в базе уже лежат селфи и скан паспорта. Предлагается показывать магазину
**фото и имя курьера**, взявшего заказ, — сейчас видно только телефон. Продавец сверяет лицо
и вправе не отдать товар.

Это независимо от списков, стоит одного блока в карточке заказа и работает даже там, где список
не заполнен. Делать вместе или отдельно — решать при планировании.

## Что НЕ делается

- Новый статус заказа.
- Таймеры, волны, автооткрытие — прямое следствие решения «не открывать никогда».
- Залог из кошелька: `top_up_enabled = false`, экономика жетонов стоит, у всех заказов
  `points_amount = 0`. Плюс это подменяет доверие имущественным цензом.
- Уровни доверия платформы (порог по рейтингу вместо списка) — обсуждались, отклонены в пользу
  поимённого списка. Поле `trusted_only` булево; если уровни понадобятся, оно станет строкой.

## Риски

| Риск | Чем гасим |
|---|---|
| Содержимое скрытого заказа читается через API | Принято осознанно: замок — право на изменение, а не на чтение. Фильтр на чтение можно добавить позже |
| Курьер вне списка получит пуш и упрётся в отказ | Фильтр пушей обязателен — прямое следствие открытого чтения |
| Курьер добавит сам себя в чужой список | Права `create`/`delete` на новой коллекции только для своих строк (`shop_id` = я) |
| Старые заказы с `NULL` пропадут из ленты | Backfill в `false` + защитная форма фильтра |
| Четыре места разъедутся: видит, но не может взять | Одно выражение в общей функции на обе ленты, оно же в праве №164 и во флоу |
| Пустой список + дорогой заказ = мёртвый заказ | Автоматика не включается при пустом списке |
| Путь фильтра на 5 уровней не поддержан | Проверяется первым шагом; запасной вариант — денормализация в заказ |
| Курьера убрали из списка, а заказ у него | Видимость касается только свободных заказов; взятый не трогается |
