# «Приведи друга» — реферальная программа курьеров

Дата: 2026-08-27

## Задача

Курьер приглашает знакомого курьера и получает 10 жетонов. Требование: очень просто
для человека — минимум действий, никаких новых понятий.

## Два факта, которые определили конструкцию

**Жетон сегодня ничего не стоит.** У всех 142 заказов `points_amount = 0` — взять заказ
бесплатно. `top_up_enabled = false` — купить жетоны нельзя. За всё время только 4 транзакции
с ненулевой суммой. Приз в 10 жетонов станет призом, когда экономика включится: тогда это
около 10 бесплатных заказов, по курсу `token_rate = 2` примерно 20 манат, почти одна доставка.

Решение пользователя: **запускаем сразу, жетоны копятся на будущее.** Это принято осознанно,
и текст в приложении не должен обещать сиюминутную выгоду.

**Больше половины одобренных курьеров не работают.**

| Активных курьеров | 27 |
|---|---|
| Ни одной доставки | **15 (56%)** |
| Хоть раз возили | 12 |
| Довезли 3 и больше | 8 |

Восемь курьеров сделали 103 доставки из 115. Отсюда главное решение: платить не за анкету,
а за работу — **после первой доставки приглашённого**. Иначе программа начнёт покупать ровно
тот товар, которого уже избыток.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Как связываются | Пригласивший вписывает номер друга **заранее**, до его регистрации |
| Когда платить | После **первой завершённой доставки** приглашённого |
| Кому приз | Только пригласившему, 10 жетонов |
| Запуск | Сразу, не дожидаясь включения экономики жетонов |

Ссылки-приглашения отвергнуты: приложение раздаётся APK вручную, магазина нет, диплинки
рвались бы. Личный код курьера отвергнут в пользу номера — номер друга курьер и так знает,
а за кодом пришлось бы лезть в приложение.

### Гонка «друг успел зарегистрироваться» — как закрыта

Слабое место выбранного варианта: если друг зарегистрируется раньше, чем его впишут, приз
не засчитается, и это порождает споры.

**Правило: пригласить можно только номер, которого ещё нет в системе.** Приложение отвечает
сразу — «этот номер уже зарегистрирован, пригласить можно только тех, кого ещё нет».

Это даёт две вещи. Во-первых, обратная связь приходит в момент ввода, а не молчаливой потерей
приза через неделю. Во-вторых — и это важнее — закрывается злоупотребление: иначе курьер мог
бы перебрать номера свежезарегистрированных чужих новичков и записать их на себя. Право на
чтение `customers` открыто, так что перебор был бы вполне реален.

Порядок действий проговаривается в тексте экрана: «впишите номер до того, как друг скачает
приложение».

## Данные

**Новая коллекция `referrals`.**

| Поле | Тип | Назначение |
|---|---|---|
| `id` | integer, auto | |
| `date_created` | timestamp | |
| `inviter_id` | m2o → `customers` | кто пригласил |
| `invited_phone` | string | нормализованный `+993XXXXXXXX` |
| `invitee_id` | m2o → `customers`, nullable | заполняется, когда друг зарегистрировался |
| `status` | string | `invited` → `registered` → `paid` |
| `reward_amount` | integer | сколько начислено, фиксируется в момент выплаты |
| `paid_at` | timestamp, nullable | |

Сумма приза копируется в строку при выплате намеренно: если завтра приз изменят, старые
записи не должны задним числом менять смысл.

**Поля в `app_settings`:**
- `referral_reward` — integer, по умолчанию `10`. **Ноль выключает программу целиком** —
  тот же рубильник, что у надёжных курьеров.
- `referral_max_pending` — integer, по умолчанию `10`. Потолок неоплаченных приглашений
  у одного курьера.

### Формат номера — обязательная нормализация

В `customers.phone` формат строго один: `+993XXXXXXXX`, 12 символов, без пробелов —
проверено на всех 43 записях, дублей нет. В `otp_codes.identifier` тот же формат.

А вот в заказах `client_phone` выглядит иначе: `+993 61 90 92 22`, с пробелами. Курьер будет
вводить номер под маской `## ## ## ##`, как на других экранах. Поэтому перед сохранением
и перед любым сравнением номер приводится к виду `+993` + 8 цифр. Без этого сверка будет
молча не находить совпадений.

## Как это работает

1. Курьер открывает «Приведи друга» в профиле, нажимает «Пригласить», вводит номер.
   Строка создаётся со статусом `invited`.
2. Друг скачивает приложение и регистрируется по этому номеру → строка получает `invitee_id`
   и статус `registered`. Курьер видит в списке «зарегистрировался».
3. Админ одобряет аккаунт как обычно — отдельного шага в программе нет.
4. Друг завершает **первый** заказ → пригласившему начисляется 10 жетонов, строка переходит
   в `paid`, приходит уведомление.

Шага «одобрен» в программе нет намеренно: он ничего не меняет для выплаты, а лишний статус
в списке отвлекал бы.

## Флоу в Directus

Все четыре построены по образцу уже работающих: «Welcome Bonus для курьера» делает ровно
то же самое — ловит событие, проверяет право на бонус, увеличивает `balance_points`, шлёт
уведомление.

**1. «Реферал — пригласить»** (webhook). Тело: `phone`.
Пригласивший берётся из `$accountability.user`, никогда из тела запроса.
Проверки по порядку, каждая со своим кодом:
- вызывающий — курьер → иначе `NOT_A_COURIER`;
- номер нормализуется и проверяется на длину → иначе `BAD_PHONE`;
- это не собственный номер → иначе `SELF_INVITE`;
- такого номера ещё нет в `customers` → иначе `ALREADY_REGISTERED`;
- этот номер ещё никем не приглашён → иначе `ALREADY_INVITED`;
- неоплаченных приглашений меньше потолка → иначе `LIMIT_REACHED`.

**2. «Реферал — отменить приглашение»** (webhook). Тело: `id` строки.
Удаляет только своё и только со статусом `invited`. Нужно, чтобы опечатка в номере не
занимала место под потолком навсегда.

**3. «Реферал — связать при регистрации»** (событие `items.create` на `customers`).
Ищет приглашение с этим номером в статусе `invited`, проставляет `invitee_id` и `registered`.

**4. «Реферал — выплата»** (событие `items.update` на `orders`).
Срабатывает, когда заказ стал `completed`. Условия:
- у заказа есть курьер;
- это его **первая** завершённая доставка (иначе за одного друга платили бы многократно);
- есть строка с `invitee_id` = этот курьер и статусом `registered`;
- `referral_reward > 0`.

Тогда: `balance_points` пригласившего увеличивается, создаётся транзакция, строка переходит
в `paid` с `reward_amount` и `paid_at`, пригласившему уходит уведомление.

⚠️ Проверка «первая доставка» и статус `registered` вместе дают защиту от повторной выплаты
с двух сторон. Одной проверки мало: флоу на `items.update` может сработать дважды.

## Приложение

Экран «Приведи друга» в профиле курьера:
- сколько жетонов уже получено и сколько друзей приглашено;
- список приглашений со статусом: «ждём регистрации» / «зарегистрировался» / «+10 жетонов»;
- кнопка «Пригласить» с полем номера под той же маской, что везде;
- у строк в статусе «ждём регистрации» — крестик для отмены.

Текст объясняет порядок прямо: сначала вписать номер, потом друг скачивает приложение.
Про жетоны говорится честно — что это, и что тратить их можно будет на заказы.

Права: чтение своих строк (`inviter_id` = я). Создание и удаление приложению **не выдаются** —
только через флоу. Причина известна: Directus не применяет связанный фильтр к праву `create`,
это проверено 27.08 при работе над надёжными курьерами, и любой пользователь смог бы вписать
приглашение от чужого имени.

## Что НЕ делаем

- Ссылки-приглашения и диплинки.
- Приз новичку — решено платить только пригласившему.
- Многоуровневые начисления «за друга друга».
- Отдельный статус «одобрен» в списке приглашений.

## Риски

| Риск | Чем гасим |
|---|---|
| Номера не совпадут из-за формата | Нормализация к `+993`+8 цифр перед сохранением и сравнением |
| Двойная выплата за одного друга | Две независимые проверки: первая доставка И статус `registered` |
| Перебор чужих новичков | Пригласить можно только номер, которого ещё нет в системе |
| Ковровое приглашение всех подряд | Потолок неоплаченных приглашений, по умолчанию 10 |
| Приглашение от чужого имени | Пригласивший берётся из авторизации; прав `create` у приложения нет |
| Самоприглашение со второй SIM | Свой номер отбивается; остальное ловит проверка паспорта при одобрении |
| Курьер решит, что приз ненастоящий | Осознанное решение пользователя; текст не обещает сиюминутной выгоды |

## Что проверено живьём (27–28.08)

**Приглашение и отмена**, под настоящим входом временного пользователя: отказ не курьеру,
свой номер, номер существующего курьера, мусор вместо номера, повтор, полный вид `+993…`,
потолок, отмена чужой и своей строки, выключенная программа. **Подсунутый в теле чужой
`inviter_id` проигнорирован** — пригласивший берётся из авторизации.

**Связывание при регистрации**: приглашённый регистрируется → строка `registered` с
`invitee_id`; посторонний регистрируется → приглашения не тронуты; повторной привязки нет.

**Выплата**, с движением жетонов на временных записях: первая доставка друга → баланс
`0 → 10`, строка `paid`, сумма и дата проставлены; вторая доставка → без изменений;
повторное завершение того же заказа → двойной выплаты нет. Баланс возвращён, все
временные записи удалены.

Случай «доставку завершает никем не приглашённый курьер» отдельной строкой не подтверждён —
проверка оборвалась на нём, — но он покрыт вторым случаем: там строка уже оплачена, и
выплаты не произошло по той же ветке кода.
